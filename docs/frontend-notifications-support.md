# 前端通知与客服模块

## 范围

通知中的柜体事件仍使用前端活动映射，客服通知与反馈会话已接入后端持久化和实时提醒。页面位于 Expo Router 的详情路由中，业务组件分别维护在
`frontend/src/features/notifications` 与 `frontend/src/features/support`。两个入口都只对已登录会话开放，
不直接访问数据库、设备或第三方服务。

## 通知流程

1. 首页铃铛展示当前账户的未读数量，并进入通知页。
2. 通知页只展示需要用户关注的异常、客服与安全消息，分为“未读”和“已读”两个标签页。
3. 柜体事件已读状态按账户保存在本地存储；客服回复的权威未读状态由后端消息 `read_at` 保存。点击客服通知时客户端先按“反馈 ID + 最新客服消息时间”立即标为已读，再同步后端，避免并行刷新用旧未读数覆盖；下一条客服回复使用新时间，因此会重新成为未读。
4. 用户只要打开客服通知或对应会话就算已读，无需发送回复；“全部已读”也会逐条调用受鉴权的已读接口。
5. 后台客服回复成功落库后发送 `support.message_created` 实时事件，事件只包含反馈 ID；客户端随后通过 REST 重新拉取权威数据。App 回前台和手动刷新提供漏消息补偿。
6. 同一回复还通过 Expo Push Service 发送手机系统横幅和应用角标。推送正文使用泛化提示，不携带客服会话正文；点击系统通知会深链进入本人会话并触发同一已读流程。前台横幅不播放声音，Android 使用 `support` 高优先级通知频道。

系统远程推送需要通知权限、EAS project ID、iOS/APNs 或 Android/FCM 凭据，以及包含 `expo-notifications` 原生配置的 development/production build。Expo Go 不支持该远程推送链路；权限被拒绝或推送服务暂时失败时，App 内通知、WebSocket 和 REST 补拉仍然可用。

柜体通知内容来自本地活动视图，只保留成员增删、权限变更和批量清空钥匙等高关注事件；普通借出、归还、钥匙增删改和撤销只进入活动审计。客服通知来自本人反馈会话的客服消息，不会把全量反馈或其他用户身份载入通知。设备异常和安全风险后续仍应使用专用后端通知数据源。

## 反馈问题流程

1. 账户页“服务支持”分组中的“反馈问题”进入表单页面。
2. 表单包含称呼、反馈类型（应用问题默认/产品问题）、可选标题、必填内容和最多 5 张图片。
3. 图片在客户端转换为 JPEG，最长边优先压缩到 1600 像素；超出单张限制时再次压缩到 1200 像素，再通过统一请求层提交。
4. 后端校验登录会话、字段、图片数量和大小，通过 SMTP 将反馈发送到配置邮箱。邮件附带唯一查询编号、提交时间、用户 ID、用户名和登录邮箱，并把登录邮箱设置为 `Reply-To`。
5. SMTP 未配置或发送失败时页面明确显示失败，不会声称已收到反馈。
6. 表单页右上角的“客服会话”按钮进入历史页，展示当前账户提交过的反馈、投递状态、未读客服回复、查询编号和时间，并支持下拉刷新。
7. 用户打开会话可查看双方完整消息时间线并继续回复；用户回复会立即写入管理后台队列，并尝试通过同一 SMTP 配置提醒客服邮箱。
8. 管理后台“客服反馈”提供检索、状态筛选、未读提示、会话详情和回复。客服回复先落库，再尝试发送用户邮件；邮件失败不会丢失 App 内消息，页面会显示投递失败状态。

反馈接口限制内容长度、附件体积和每小时请求频率。后端日志只记录失败上下文中的用户 ID 和反馈编号，不记录反馈正文、附件、邮箱密码、门禁凭据或设备密钥。业务数据库保存反馈文字、身份快照、图片数量和投递状态供本人历史查询，图片文件/Base64 只用于当次邮件发送且不会重复保存。通用审计日志仍只保存类型、图片数量、结果和失败码。

## 权限与异常边界

- 两个页面由 `(details)` 登录守卫保护；会话失效时返回登录流程。
- 通知只展示当前账户有权查看的高关注事件、异常和客服消息。
- 本地柜体通知状态读取或写入失败时保留当前内存状态；客服点击后即时更新本地状态，服务端同步失败时后续联网刷新会重新校准。
- 反馈页提供图片压缩、发送中、发送成功编号、失败和重试状态。
- 客服列表、详情、已读和回复接口都在 SQL 层按会话用户 ID 过滤；前端路由守卫不能替代后端归属校验。
